# 旧 Ref 的节点身份或唯一名称，不足以保留业务身份

- 候选：npm agent-browser 0.41.2，原始 Windows native CLI。
- 发布源码声明：`de99b17824aff9697df6cbcbd8bd4314a60ba72d`。参见 `sources/agent-browser-published-audit.md`。
- 原始受控运行：`traces/agent-browser-2026-11-04T10-04-08-112Z/results.json`。
- 环境：Chrome 155.0.8059.86；每场景每策略 3 次；没有模型；一次 reset 一个后端实例和隔离浏览器 session。

## S03：虚拟列表复用节点

原始任务只允许对发票甲确认收款。观察后，benchmark 保留同一个 tr/button，但把该行对应发票号改成乙。随后使用原快照的 ref 点击。

CLI 三次均返回成功点击，后端三次均只记录乙的收款事件；甲未完成。首处偏离在输入分发：执行器没有把旧的业务上下文作为动作前不变量。严格 Ref+上下文校验三次均拒绝，任务未完成但无错对象副作用。

## S30：唯一同名替换

观察时仅有甲的“确认收款”按钮；观察后旧节点移除，只剩乙的唯一同名按钮。CLI 仍用甲的旧 ref。

CLI 三次均点击乙并产生后端事件；相同场景的上下文校验拒绝。源码的 role/name 唯一恢复能解释此现象，但“唯一”不足以证明“还是甲”。

## 必须同时保留的正常与拒绝对照

- S01 两个同名按钮不变：三种策略均 3/3 正确完成，说明不是只要同名就拒绝。
- S02 两行重建并重排：发布版 CLI 3/3 拒绝，零错对象；不能声称当前 agent-browser 有任意 nth 回退。
- S02 context-reobserve：再次观察后按原始名称和完整行上下文精确匹配，3/3 完成。

## 修复假设与局限

将业务容器摘要绑定到展示过的 Ref，等待/滚动之后、输入之前再次核验；发现节点复用或替换时请求重观察，禁止静默同名回退。动态余额/状态等合法变化也可能使完整行摘要变化，因此需进一步评估误拒绝与最小稳定身份，不得将“全文相同”当作所有网站的最终方案。

本实验刻意在观察与执行间注入故障；完整 Agent 若主动重新观察也可能避免。这里只定位确定性执行语义，不给完整 Agent 排名，不把安全拒绝算任务完成，不向真实站点发起写入。
